# Assumptions Log — Lumen Lyceum EdTech Analytics

Running list of judgment calls made while building the pipeline, since the source data is deliberately imperfect and several definitions are ambiguous by design.

| # | Assumption | Why | Where it's applied |
|---|---|---|---|
| 1 | The *latest graded* assessment attempt represents an enrolment's exam outcome, not the first attempt or the highest score across attempts. | The gateway logs every attempt including failed retries; "did they eventually pass" is the more decision-relevant question for credentialing than "did they pass on try 1." | `stg_assessments.sql` |
| 2 | Attempts with `attempt_status = 'submitted'` (not yet graded) are excluded from the outcome model entirely, rather than treated as incomplete/failed. | A submitted-but-ungraded attempt has no determined outcome yet; including it as "not passed" would understate true pass rates once grading catches up. | `stg_assessments.sql` |
| 3 | A lesson is deduplicated by keeping the row with the latest `completed_at` when the same `enrollment_id` + `lesson_number` + `lesson_status` appears more than once (device-switch case). | The README explicitly flags this as a known data-quality issue, not a modeling choice to leave ambiguous. | `stg_lessons.sql` |
| 4 | "Curriculum complete" = 100% of a course's lessons marked completed (not a partial threshold like 80%). | No partial-completion threshold was specified in the engagement brief; 100% is the least ambiguous reading of "finished the lessons." | `int_lesson_completion.sql` |
| 5 | The 28-day active-learner window is measured from `enrolled_at` (i.e., "was there any activity within 28 days of enrolling"), not a rolling window measured from the current date. | This matches a cohort-based engagement metric more naturally than a point-in-time snapshot; flagged explicitly since the alternative (rolling from today) is equally plausible and changes the metric's meaning. | `fct_enrollments.sql` — **swap logic here if the original engagement brief specifies rolling** |
| 6 | The unit of analysis is the enrolment (`enrollment_id`), not the learner (`student_id`) — a student who re-enrols or takes multiple courses produces multiple independent rows. | Explicitly stated in the engagement brief: "the unit of analysis is an enrolment... not a person." | All models |
| 7 | The platform's own `enrollment_status` field is treated as an untrusted, separately-reported signal — never used as a source of truth for completion — and is instead compared against the two modeled definitions to detect disagreement. | The engagement brief states this status "doesn't always agree with the underlying events"; the reconciliation deliverable specifically requires surfacing that disagreement, not resolving it silently. | `fct_enrollments.completion_reconciled`, `mart_completion_reconciliation.sql` |
| 8 | Test severities were assigned by business impact, not applied uniformly: grain/join integrity issues (`unique`, `not_null`, `relationships`) are `error`; less catastrophic anomalies (a new/unexpected bucket in `completion_reconciled`) are `warn`. | A broken grain silently corrupts every downstream metric and should stop the pipeline; a new category value is worth investigating but shouldn't block a daily load. | Test severities across all model `.yml` files |
| 9 | The orchestration DAG assumes the platform's daily export completes by roughly 2 AM, scheduling the pipeline at 3 AM as a fixed fallback, with a freshness check as the actual gate. | No real upstream SLA was provided in the engagement materials; this is a reasonable placeholder assumption to make the DAG design concrete, not a confirmed SLA. | DAG design, Deliverable 5 |

**Update:** the raw-timestamp corruption bug referenced throughout this log and the README (`enrolled_at`/`last_active_at` loading as nonsensical dates via the data generator's `write_pandas` step) has since been fixed at the source. The generator was corrected and the raw tables reloaded with valid 2024-2025 dates. `active_within_28_days`, `days_active_span`, and `median_days_to_complete` are now confirmed correct: 31.4% active learners (28-day window), 45-day median time-to-complete.
